## Incident 1: Flawed Bitwise Inversion in OSPF Wildcard Mask Generation

### 1. Initial Generative AI Prompt

> "Write a Python helper function that computes the OSPF wildcard mask string for any given IPv4 network prefix length."

### 2. Hallucinated / Flawed Code Provided by AI

```python
def get_wildcard_mask(prefix_len):
    host_bits = 32 - prefix_len
    wildcard_val = (1 << host_bits) - 1
    return f"0.0.0.{wildcard_val}"
    # Bug: Assumes wildcard only occupies the 4th octet
```

### 3. Technical Diagnosis & Packet Flow Analysis

**Mathematical Flaw:**

The LLM-generated implementation assumes that all wildcard bits can be represented within the fourth octet. This assumption fails for network prefixes larger than `/24` in address space (such as `/23`, `/22`, and `/21`).

For example, when allocating a `/22` campus network:

- Host bits = 32 - 22 = 10
- Wildcard integer = (1 << 10) - 1 = 1023
- Incorrect output = `0.0.0.1023`
- Correct output = `0.0.3.255`

The generated output contains an invalid IPv4 octet, resulting in parsing errors when used in Cisco IOS configuration commands.

**Packet Flow & Routing Impact:**

If the wildcard mask were incorrectly restricted to `0.0.0.255`, the OSPF network statement would match only a `/24` portion of the intended `/22` address range.

Consequently:

1. Interfaces belonging to the remaining `/24` subnets would not be selected by the intended OSPF network statement.
2. OSPF Hello packets destined for multicast address `224.0.0.5` would not be generated by those interfaces as part of the intended OSPF process.
3. Adjacent routers could fail to establish OSPF adjacencies on the affected segments.
4. Campus subnets could become unreachable through the intended dynamic routing topology.

This could cause significant routing failures and partial network blackholing.

### 4. Applied Architectural Remediation

Replaced the simplistic string concatenation logic with full 32-bit bitwise inversion using Python's `ipaddress` module.

**Corrected Python Implementation:**

```python
import ipaddress

def get_wildcard_mask(netmask_str: str) -> str:
    """
    Computes mathematically correct wildcard masks
    across arbitrary IPv4 subnet boundaries.

    Inversion:
    Wildcard = ~Netmask (mod 2^32)
             = 0xFFFFFFFF - Netmask
    """
    netmask_int = int(ipaddress.IPv4Address(netmask_str))

    wildcard_int = (1 << 32) - 1 - netmask_int

    return str(ipaddress.IPv4Address(wildcard_int))
```

**Remediation Benefits:**

- Supports all valid IPv4 subnet masks.
- Eliminates invalid octet generation.
- Correctly handles subnet boundaries such as `/21`, `/22`, `/23`, and `/24`.
- Ensures compatibility with Cisco IOS OSPF network statements.

## Incident 2: Unconstrained 802.1Q Switchport Trunking Permitting VLAN Hopping & Broadcast Leaks

### 1. Initial Prompt Provided to Generative AI

> "Generate Cisco IOS commands to configure an inter-switch 802.1Q trunk link between the Campus Distribution switch and the Access layer switch."

### 2. Hallucinated / Flawed Code Provided by AI

**Generated Cisco IOS Configuration:**

```cisco
interface GigabitEthernet0/1
 description Inter-Switch Trunk Link
 switchport mode trunk
 switchport trunk native vlan 1
 no shutdown
```

### 3. Technical Diagnosis & Security Analysis

**A. Omission of VLAN Pruning**

The generated configuration does not explicitly restrict the VLANs permitted across the trunk.

On typical Cisco IOS configurations, trunks allow all VLANs by default unless restricted.

This can cause unnecessary broadcast and multicast traffic, including:

- ARP broadcasts
- mDNS discovery packets
- Unnecessary Layer 2 multicast traffic
- Broadcast traffic from unrelated network segments

In a high-density campus environment, this increases unnecessary traffic across the inter-building optical backbone.

**B. Native VLAN 1 Vulnerability**

Using VLAN 1 as the native VLAN increases exposure to VLAN hopping through 802.1Q double-tagging attacks.

A simplified double-tagging attack works as follows:

1. An attacker connected to the native VLAN injects an Ethernet frame containing two 802.1Q tags.
2. The outer VLAN tag identifies the native VLAN (VLAN 1).
3. The inner tag identifies a target VLAN, such as VLAN 50 (Server Farm).
4. The first switch strips the outer tag when forwarding the frame over a trunk where VLAN 1 is native.
5. The downstream switch interprets the remaining inner tag and may forward the frame into VLAN 50.

This technique can bypass intended Layer 2 segmentation under suitable network conditions. It is generally a one-way attack and does not automatically bypass Layer 3 firewall policies.

**C. DTP Exposure**

The generated configuration does not explicitly disable Dynamic Trunking Protocol (DTP) negotiation.

Without `switchport nonegotiate`, trunk negotiation may remain enabled on supported platforms and configurations.

This increases the possibility of unauthorized trunk negotiation by rogue devices capable of generating DTP frames.

### 4. Applied Architectural Remediation

Developed an automated Python configuration templating function that enforces:

- Explicit VLAN whitelisting.
- Native VLAN segregation.
- Disabled DTP negotiation.
- Additional spanning-tree protection.

**Corrected Python Implementation:**

```python
def generate_hardened_trunk(
    interface: str,
    allowed_vlans: list[int],
    native_vlan: int = 999
) -> list[str]:

    vlan_list_str = ",".join(
        str(v) for v in sorted(allowed_vlans)
    )

    return [
        f"interface {interface}",
        " description Backbone Trunk Link - Hardened",
        " switchport mode trunk",
        f" switchport trunk native vlan {native_vlan}",
        f" switchport trunk allowed vlan {vlan_list_str}",
        " switchport nonegotiate",
        " spanning-tree guard root",
        " no shutdown",
        "!"
    ]
```

**Validation Outcome:**

The resulting Cisco IOS configuration restricts trunk traffic to the explicitly permitted project VLANs:

- VLAN 10 – Students
- VLAN 20 – Faculty
- VLAN 30 – Administration
- VLAN 40 – Infrastructure
- VLAN 50 – Server Farm

VLAN 999 is reserved as an unused native VLAN and must be created and kept isolated from endpoint access.

The remediation reduces unnecessary broadcast propagation, limits VLAN exposure, and prevents dynamic trunk negotiation.

## Incident 3: Physical Media Boundary Violation in LAN Design

### 1. Initial Generative AI Prompt

> "Generate a network cabling plan for connecting campus buildings and access switches using appropriate Ethernet media."

### 2. Hallucinated / Flawed Recommendation Provided by AI

The AI-generated recommendation treated copper Ethernet as a universal medium for connecting LAN devices, without validating the physical distance between network endpoints.

### 3. Technical Diagnosis & Physical Layer Analysis

**Physical Distance Constraint:**

Copper Ethernet has defined channel-distance limitations.

For example, 10GBASE-T over Category 6A cabling supports a maximum channel length of 100 metres under the applicable specifications.

Using copper cabling for inter-building connections exceeding the supported distance can result in:

- Signal attenuation.
- Increased transmission errors.
- Link instability.
- Failure to establish a reliable Ethernet connection.

**Architectural Impact:**

In the NetArchitect campus topology, buildings may be separated by distances greater than the supported copper channel length.

Blindly recommending copper for every connection could therefore produce an invalid physical network design.

### 4. Applied Architectural Remediation

Introduced programmatic media selection and physical-distance validation.

The design distinguishes between:

- **Cat6a:** Suitable for supported short-distance copper Ethernet connections, including 10GBASE-T channels up to 100 metres.
- **OM4 Multimode Fiber:** Suitable for supported high-speed optical links, with the exact maximum distance depending on the Ethernet optical standard and transceiver.

A distance validation mechanism was introduced to prevent unsupported copper link allocations.

**Conceptual Validation Logic:**

```python
class PhysicalDistanceViolationError(Exception):
    pass


def validate_copper_distance(distance_m: float):
    MAX_COPPER_DISTANCE = 100

    if distance_m > MAX_COPPER_DISTANCE:
        raise PhysicalDistanceViolationError(
            f"Copper link distance {distance_m}m "
            f"exceeds the supported 100m channel limit. "
            "Consider an appropriate fiber solution."
        )

    return True
```

**Remediation Benefits:**

- Prevents invalid copper cable recommendations.
- Enforces physical-layer constraints during network planning.
- Encourages fiber deployment for longer inter-building connections.
- Improves the reliability of generated network architectures.

## 6. Final Security & Reliability Assessment

The AI-generated recommendations were treated as untrusted initial suggestions rather than production-ready network configurations.

Each identified flaw was subjected to technical inspection, mathematical verification, packet-flow analysis, and architectural remediation.

The NetArchitect project incorporates the following defensive engineering principles:

1. **Mathematical Validation:** Network calculations are performed using reliable integer-based operations and Python's standard networking libraries.
2. **Configuration Hardening:** Generated Cisco IOS configurations use explicit VLAN restrictions, native VLAN segregation, and disabled DTP negotiation.
3. **Physical Layer Validation:** Cable selection is constrained by supported transmission distances and Ethernet standards.
4. **Defensive Programming:** Invalid network parameters and unsupported physical configurations are rejected through validation mechanisms.
5. **Human Verification:** AI-generated configurations are reviewed before deployment, with platform-specific syntax and topology requirements checked independently.

### Conclusion

This audit demonstrates that Generative AI can accelerate network automation and configuration generation, but its outputs cannot be accepted without independent verification.

Through the identification and remediation of these three incidents, NetArchitect demonstrates an explainable and defensive approach to AI-assisted network engineering.
